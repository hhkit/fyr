\begin{abstract}
It has been about two decades since the raster pipeline of the GPU was first used for general compute, sparking off a worldwide, multi-decade, multi-trillion dollar investment into accelerating linear algebra on hardware initially designed for entertainment. With the advent of artificial intelligence, the majority of the research effort has largely been directed towards generalizing the rendering hardware such that it is more usable by generic compute workflows. In particular, linear algebra stands out as the class of programs that is trivially easy to optimize for the GPU, due to the parallelizability of its underlying algorithms. In lieu of this observation, custom architectures spring up in an attempt to further optimize linear algebra workflows. However, we observe that consumer-grade GPUs across all vendors continue to retain hardware accelerators and pipelines designed specifically for computer graphics, with texture samplers and ray tracing acceleration structures as examples. Such functionality goes largely ignored or unused by the majority of the high performance computing community.

Our thesis is as follows: compiling to optimize a program for the GPU is more than just tiling parallelizable loops generically and instruction selection. We aim to repeat history with GPU architecture, to open up the raytracing pipeline and other aspects of graphics-oriented architecture to a wider class of programs. These pipelines have already been proven to improve performance outside of computer graphics; our goal is to provide a workflow for engineers to invisibly take advantage of these pipelines without needing to understand the underlying hardware architecture. We will achieve this by using MLIR's hybrid IR to handle \emph{pipeline semantics} separately from computations, designating specific operations for specialized pipelining and then fusing dependent operations into the resulting kernels.

Surprisingly, there is an existing class of programs that currently utilizes all three pipelines of the GPU. Real-time simulations utilize raytracing to calculate global illumination, the raster pipeline to render the scene, and the compute pipeline for miscelleanous computations such as animation skeleton updates and physics. To demonstrate the flexibility of enabling and optimizing for pipeline semantics, we will attempt to declaratively define and optimize the engine for a real-time interative simulation.

In summary, we will attempt to answer the following research questions:
\begin{itemize}
  \item RQ1: What are the restrictions with regards to optimizing linear algebra programs?
  \item RQ2: What is a suitable abstraction for designating parts of a program to use the raytracing pipeline, such that we can apply compiler techniques to achieve a performant program that fully utilizes all capabilities of the GPU?
  \item RQ3: Can program rewrites reduce the performance gap between raytraced and rasterized workflows in real-time scenarios? 
\end{itemize}
\end{abstract}

\section{Literature Review}

This literature review will span the three topics that the thesis will cover: the GPU architecture, compilers, and computer graphics.

\subsection{GPU and General Purpose Compute}

\emph{Note: GPU terminology is not standardized and inconsistent across vendors. This section will be using Nvidia's terminology, but where modern features are concerned, similar terminology for the vendor-agnostic Vulkan \cite{vulkanHomeVulkanCross2025} will be mentioned as well.}

\begin{figure}
  \includegraphics[scale=0.5]{GPUArchitecture.pdf}
  \caption{A heavily simplified block diagram of Nvidia's GB202 GPU, also known as the RTX 5090 \cite{NVIDIABlackwellArchitecture2025}. \label{fig:gpuarch}}
\end{figure}

The GPU, or graphics processing unit, is a single-instruction multiple-data (or SIMD) architecture that consists of a massive number of streaming multiprocessors (or SMs) \autoref{fig:gpuarch}. A streaming multiprocessor consists of a set of CUDA cores and a set of warp schedulers, and execute bundles of threads known as warps. On Nvidia architectures, an SM receives a warp of 32 threads that share four warp schedulers. % Pre-Volta, threads would conditionally execute the same instruction eight times in parallel four times in sequence for the total of 32 threads. However, as of Volta, each thread has its own program counter, and programmers are encouraged to treat each thread as its own instance in a paradigm known as SIMT (single-instruction multiple-thread). The underlying hardware attempts to retain the performance granted by SIMD by grouping threads with similar control flow, however, if inter-lane control flow diverges too much, they become subject to performance degradation in what is known as \emph{warp divergence}.

Each streaming multiprocessor is also home to a set of \emph{application-specific integrated circuits} for accelerating common functions. Tensor cores allow for fast tensor fused-multiply-and-add across the warp, and ray tracing cores accelerate the triangle-ray intersection operation. Moreover, due the GPU's historic purposes, streaming multiprocessors also have access to \emph{texture mapping units} (TMUs) that accelerate linear, bilinear, and trilinear interpolation of values in the bound texture.

\paragraph{Programming for the GPU} To program for the GPU, programmers write what is known as a \emph{kernel}. The kernel is executed over a large number of threads known as a \emph{grid} which is a tuple $(G,B)$ of $G$ thread blocks each containing $B$ threads for a total of $G \cdot B$ threads in a dispatch. Each invocation of the kernel is assigned a block identifier and a thread identifier, allowing the program to branch based on the invocation identifier. Within a block, threads are able to share memory and synchronization primitives, although grid-level synchronization is made available by a driver. On kernel dispatch, each block is issued to a streaming multiprocessor, which then partitions the block into warps for execution. Programmers for Nvidia architectures may use CUDA to write kernels, and for programmers who wish to target a wider variety of hardware, they may write the kernel as a compute shader compiled to SPIR-V and execute it using the Vulkan API.

Typically, a kernel dispatch is performed from the CPU (also known as the host device). However, the ability to dispatch kernels from the GPU grows increasingly supported, reducing the need for ping-pong between the CPU and GPU. In CUDA, the feature is known as \emph{Dynamic Parallelism} \cite{adinetCUDADynamicParallelism2014}, and in Vulkan, the extension is known as \emph{Device-Generated Commands} \cite{VK_EXT_device_generated_commands3VulkanDocumentation}.

\subsection{Compilers for the GPU}

As a massively parallel architecture, compilers for the GPU are closely associated with parallel compilers.

\newcommand{\domain}{\mathbb{D}}

\subsubsection{Loop optimizations} Loop optimizations are a set of program transformations that target loops; specifically, they target \emph{perfectly nested loops}. Perfectly nested loops are crucial for loop optimization, as by having no statements in between loop headers, the loop can be compactly represented as a 2-tuple of its iteration domain $\domain \in \mathcal{P}(\mathbb{Z}^{n})$ and its body $S \in \domain \to \mathcal{D}_S$, and transformations can be made to either the iteration domain or the statement without necessarily reasoning about the other. We demonstrate this with a C/C++ example, but also present a corresponding notation to simply the syntax and emphasize changes effected by loop transformations. For loops deemed to be embarrassingly parallel, we shall denote them with $\mathbf{for~all}$ instead of $\mathbf{for}$.

\begin{tabular}{p{0.46\textwidth}p{0.46\textwidth}}
\begin{minted}{cpp}
#pragma omp parallel 
for (int i = 0; i < 1024; ++i)
    for (int j = 0; j < 32; ++j)
S:      c[i] = c[i] + a[i][j];
\end{minted}
&%

\begin{algorithmic}
  \State $\mathsf{let }~ \lBrack  S \rBrack (i,j) \triangleq \left( c_i := c_i + a_{i,j} \right) ~\mathsf{in}$ 
  \ForAll {$i \in [0,1024)$}  
    \For {$j \in [0, 32)$}  
      \State $ \lBrack  S \rBrack (i,j) $
    \EndFor
  \EndFor
\end{algorithmic}
\vfill
\end{tabular}

As in many loop optimization models \cite{xueUnimodularTransformationsNonperfectly1997,grosserPolyhedralASTGeneration2015}, we will assume the program iterates through $\domain$ lexicographically. The specific invocation of a statement $S$ executed with induction variables $v \in \domain$ is denoted as $S_{v \in \domain}$, and the set of all statement invocations as $\mathcal{D}_S$.  The dependency relation $\mathbf{D}_r : \mathcal{D}_S \times \mathcal{D}_S $ may be derived with program analysis, and defines a partial order on the statement invocations that must be fulfilled to preserve the semantics of the executing program. 

We now define a loop transformation $T: \domain \to \domain$ as a transformation of a loop's iteration domain. For $T$ to be a legal transformation, it must preserve program semantics, which requires the dependency relation to remain satisfied under $T$ (i.e. $\forall (S_u,S_v) \in \mathbf{D}_r . (S_{T(u)}, S_{T(v)}) \in \mathbf{D}_r$).

While there are a myriad of loop transformations such as loop reversal, loop skewing, and loop unrolling, we will specifically discuss the two loop transformations that are required in any loop optimizing framework targeting the GPU: \emph{loop tiling} \cite{xueTilingLoopTransformation2011,wonnacottScalabilityLoopTiling2013} and \emph{loop fusion} \cite{manjikianFusionLoopsParallelism1997, darteComplexityLoopFusion1999,qiaoLoopFusionKernel2019,mehtaRevisitingLoopFusion2014}. 

\paragraph{Loop tiling} Loop tiling splits a loop dimension into multiple smaller dimensions. Tiling is a crucial transformation as perfectly nested loops are \emph{closed} under tiling, allowing the inner loops to be extracted as kernels \cite{wonnacottScalabilityLoopTiling2013} and be further tiled for lower-level optimizations such as vectorization.

\paragraph{Loop fusion} Loop fusion refers to the fusion of dependent loops to reduce the cost of iteration, removes intermediate values, or, when combined with tiling, allows for the extraction of more complex kernels. We demonstrate this below by fusing a transpose into a matrix multiplication --- a common fusion that exploits the cache in the CPU.

\subsubsection{Polyhedral compilers} Polyhedral compilers \cite{grosserPolyhedralASTGeneration2015,popGRAPHITEPolyhedralAnalyses2006,baghdadiTiramisuPolyhedralCompiler2019,sadayappan298PUBLICATIONS8186} are compilers that operate on perfectly nested affine loops known as static control parts (or SCoPs). By restricting array accesses to affine expressions on loop induction variables, formulas can be derived to calculate statistics about programs such as memory limits, cache locality that can then be optimized for. Moreover, loop transformations can be expressed as affine transformations on the loop induction variations, making polyhedral programs closed under loop transformations and can be recursively optimized.

Work has also been done on directly targeting the GPU \cite{verdoolaegePolyhedralParallelCode2013}, by tiling the SCoP and using affine expressions to compute the memory requirement of the subtile being dispatched to the GPU.

\subsubsection{User-schedulable languages} User-schedulable languages \cite{visserStrategoLanguageProgram2001, ragan-kelleyHalideDecouplingAlgorithms2017,chenTVMAutomatedEndtoEnd2018, ikarashiExo2Growing2025} refer to programming languages that specify two languages, a declarative language to describe the computation of the program, and a scheduling language to describe the optimization and gradual lowering of the program to the hardware. This achieves separation of concerns when reasoning about the numerics of the computation versus its performance.

\subsubsection{Hybrid IR: SSA and Regions} LLVM's MLIR \cite{lattnerMLIRCompilerInfrastructure2020} framework specifies an SSA-driven hybrid IR that organizes high- and low-level semantics into separate \emph{dialects}. In MLIR, operations may have regions that contain basic blocks that contain operations, allowing for operations of different dialects to coexist.

\subsection{GPU and Processing Graphics}

As we saw with general compute, computing on the GPU has come a long way from being a fixed-function pipeline, manually plugging in transformation matrices and lights to draw to the screen texture \cite{segalOpenGLTMGraphicsSystem1994}. However, while data center GPUs \cite{NVIDIABlackwellArchitecture2025} have discarded their graphical capabilities to further accelerate block \cite{rouhaniMicroscalingDataFormats2023} and tensor \cite{markidisNVIDIATensorCore2018} operations, consumer grade GPUs retain their historic purpose: graphics processing. In other words, the compute pipeline, while the most general, is far from the only pipeline available on the GPU. In fact, there are two other pipelines dedicated to graphics rendering available:
\begin{itemize}
  \item Raster pipeline (\autoref{fig:rasterpipe})
  \item Raytracing pipeline (\autoref{fig:raytracepipe})
\end{itemize}

To dispatch work to the GPU and select the appropriate pipelines, render engines interface with the graphics card using low-level APIs such as DirectX \cite{stevewhimsDirect3D12Reference}, Metal, and Vulkan \cite{vulkanHomeVulkanCross2025}. One common abstraction implemented by graphics engines, such as O3DE \cite{O3DERenderHardware} and NVIDIA-RTX \cite{nvidiaNVIDIARTXNVRHI2025}, is to abstract access to the underlying API with a \emph{rendering hardware interface} (RHI), which allows for multi-API targeting while restricting optimization for API-specific features.

\subsubsection{The Raster Pipeline}

The raster pipeline (\autoref{fig:rasterpipe}) is what directs the graphics card to transform vertex buffers through primitives into fragments that get written into the output texture. Vertex, tesselation and geometry shaders are collectively the \emph{geometry} step of the raster pipeline, producing primitives that are then rasterized into fragments that are \emph{shaded} by the fragment shader.

\begin{figure}
\includegraphics[scale=0.50,keepaspectratio]{RasterPipeline.pdf}
\caption{The raster pipeline.\label{fig:rasterpipe}}  
\end{figure}

\paragraph{Deferred Shading} As there are far more fragment shader invocations than vertex shader invocations, significant gains are made by not performing expensive lighting computations. Deferred shading defers the lighting computation to a separate render pass, painting the intermediate values required by the rendering equation into a set of output textures known as the geometry buffer (or G-buffer). While this improved the performance of lighting computations, deferred shading was notoriously memory intensive. As an embarrassingly parallel operation, however, the deferred shading computation could be tiled, saving the memory limits of the G-buffer.

\paragraph{Forward+} Forward rendering refers to performing the entire graphics pass, from geometry through to shading, in a single render pass. Forward+ \cite{haradaForwardBringingDeferred2012} takes the tiling of the deferred shading pipeline and applied it to forward rendering, tiling the camera frustum and performing frustum culls of the lights in the scene using a compute shader. The insight drawn from Forward+ was that deferred shading was not the final destination of graphics optimization; the true cost may be memory traffic. 

\paragraph{Post-processing} While the typical graphics pass produces a realistic image of the scene, many applications of real-time graphics are typically geared towards entertainment such as video games. Complete realism may not always be the requirement, and thus, artists may tune the final image, applying \emph{post processing effects} such as depth of field\cite{mcintoshEfficientlySimulatingBokeh2012} and tone mapping \cite{eilertsenRealtimeNoiseawareTone2015} to achieve a desired effect on the viewer. As each of these effects forms, massive performance gains can be made by \emph{fusing} adjacent passes into a single shader, avoiding the materialization of intermediate textures and minimizing the number of draw calls.

\subsubsection{The Raytracing Pipeline}

The raytracing pipeline (\autoref{fig:raytracepipe}) is a different pipeline that graphics programmers can opt to use that is optimized for raytracing workflows. Rays are generated by the Ray Generation Shader (RGS), which are then raycast into a hardware-accelerated bounding volume hierarchy (BVH) utilizing the raytracing core ASICs. The standout features of the raytracing pipeline are the hardware accelerated raycasts, which are non-programmable, and the option to loop back to a previous stage of the pipeline without another draw call.

\begin{figure}
\includegraphics[scale=0.55,keepaspectratio]{RaytracePipeline.pdf}
\caption{The ray tracing pipeline and its associated acceleration structures (AS). \label{fig:raytracepipe}}  
\end{figure}


\subsubsection{The Rendering Equation}

Ultimately, both render pipelines were designed to solve the render equation \cite{kajiyaRenderingEquation1986}, defined in \autoref{eqn:rendering}, which is the equation used to compute the value of a point's irradiance. The computation is done by integrating over the hemisphere $\Omega$, taking in as input the normal at the point $\mathbf{n}$ and incoming and outgoing radiance $L_i$ and $L_o$ along the directions $\omega_i$ and $\omega_o$ respectively. $f$ most often appears as $f_r$, known as the bidirectional reflection function, which is the proportion of light reflectioned from $\omega_i$ to $\omega_o$.
\begin{align}
  \label{eqn:rendering}
  \int_\Omega L_i(\omega_i)f(\omega_i,\omega_o,\theta)\langle \mathbf{n}, \omega_i \rangle \mathsf{d} \omega_i
\end{align}

The integral over the hemisphere is what allows for computing global illumination in a realistic manner. By nature of being an integral over a 2D manifold, it is also computationally intensive, yet must be performed for every fragment in the render target to achieve realistic lighting. In real-time workflows, radiance probes \cite{silvennoinenRealtimeGlobalIllumination2017} placed throughout the scene collect global illumination. Radiance cascades \cite{RadianceCascadesPaperOut_latexmk2RadianceCascadespdf} are a modern technique that utilize the mipmap feature of TMUs to accelerate the interpolation of irradiance data from adjacent radiance probes.

\subsection{Compilers in Computer Graphics}

Computer graphics as a field is huge, spanning different rendering techniques and the use of machine learning in various parts of the render pipeline. We will hence cover a small subset of it relevant to this PhD, specifically targeting the use of compiler techniques in computer graphics. 

\subsubsection{Domain Specific Languages (DSLs) for Computer Graphics}
A number of DSLs have been devised, some specfically for computer graphics, others for more generic computation. Taichi \cite{huTaichiLanguageHighperformance2019} is a high-performance DSL written for Python that is designed for high performance sparse programs, a class of programs that includes raytraced rendering. LuisaRender \cite{zhengLuisaRenderHighPerformanceRendering2022} and RenderKernel \cite{yangRenderKernelHighlevelProgramming2024} are two attempts at creating a high-level DSL for raster pipelines, attempting to use Python's decorator functionality to specify which pieces of code are kernels to be dispatched to the GPU.

\subsubsection{Inverse Rendering}

Inverse rendering derives geometry and materials from one or more final images of a target scene. This is achieved through machine learning; specifically, the approach of \emph{differentiable rendering} uses \emph{automatic differentiation} (or autodiff) of the shaders to produce geometry and textures that would produce the same target images. State of the art in the field includes Mitsuba (and its underlying IR, DR.JIT \cite{jakobDRJITJustintimeCompiler2022}), which is able to automatically differentiate the whole pipeline and train for both geometry and render simultaneously, and SlangD \cite{bangaruSLANGDFastModular2023}, which performs automatic differentiation at the per-shader level which improves performance but forces geometry and render to be trained separately. Crucially, both papers include performance comparisons with the autodiff in machine learning frameworks such as JAX \cite{frostigCompilingMachineLearning2018} and Enzyme \cite{enzymeadEnzymeCon2023HackableAutodiff2024}. We include this as an interesting exploration of compiler techniques in computer graphics, and a potential research pivot should initial plans go awry.

\section{Thesis Proposal}

When certain conditions are right, compilers are fantastic at doing certain types of automatic optimization: in particular, loop fusion and loop tiling. However, other types of optimization require guidance, either because transformations are mathematically illegal or just impossible to derive. User-schedulable languages provide a means to specify the optimization schedule manually, however, users are required to either specify every step of compiler optimization or leave it up to a previously-derived pipeline. In the domain of GPU programming, where tensor and parallel programs dominate the problem space, we propose that the compiler only needs a little bit of guidance, and all subsequent tilings, fusions, and peephole optimizations may be left up to the compiler to greedily perform.

To address each, we are proposing the following papers, each targeting a different optimization technique on the GPU:
\begin{itemize}
  \item Extensible Compiler Optimization of Attention Kernels (In Progress)
  \item Compiling to Accelerate Block-Sparse Linear Algebra with Raytracing Hardware
  \item Automatic End-to-End Optimization of Real-Time Graphics Engines
\end{itemize}

\subsection{Extensible Compiler Optimization of Attention Kernels}

Collaborator(s): Kunwar Grover, AMD \\
Workshop Demo: C4ML @ CGO (1 February 2026) \\
Target venue: OOPSLA 2026 (17 March 2026)
\newcommand{\Attention}{\mathsf{Attention}}
\newcommand{\softmax}{\mathsf{softmax}}
\begin{align}
  \label{eqn:attention}
  \quad \Attention(\mathbf{Q}, \mathbf{K}, \mathbf{V}) 
  &= \softmax(\mathbf{Q} \mathbf{K}^T) \mathbf{V}
  \\
  \label{eqn:attention-math}
  &=\left[
    \cfrac {e^{\mathbf{S}_{i,j}}} 
           {\sum_{n=0}^{N} e^{\mathbf{S}_{i,n}}}
    \right]
    \mathbf{V}
    \qquad \text{ where } \mathbf{S} = \mathbf{Q} \mathbf{K}^T
  \\
  \label{eqn:attention-math-safe}
  &=\left[
      \cfrac {e^{\mathbf{S}_{i,j} - m_i}} 
             {\sum_{n=0}^{N} e^{\mathbf{S}_{i,n} - m_i}}
    \right]
    \mathbf{V}
    \qquad \text{ where } m_i = \max_{i}(\mathbf{S}_i)
\end{align}

The attention mechanism (\autoref{eqn:attention}) is the mechanism that gives large language models the ability to infer context. As it has rather famously been decreed to be "all you need" \cite{vaswaniAttentionAllYou2023}, optimization of attention has become a heavily researched topic \cite{daoFlashAttentionFastMemoryEfficient2022,daoFlashAttention2FasterAttention2023,dongFlexAttentionProgramming2024}, especially with regards to targeting the GPU. The state-of-the-art in the field is PyTorch's FlexAttention \cite{dongFlexAttentionProgramming2024}, which admits a large variety of attention variants by providing two key configuration points: $\mathsf{score\_mod}$ to modify the values of $QK^T$ and $\mathsf{mask\_mod}$, a heavily configurable masking engine. Our key insight is that by manually specifying the optimization of one step of the attention kernel, the rest of the mechanism becomes completely configurable by the user, while leaving the compiler free to perform automatic compiler optimizations that distribute the kernel to the GPU.

\subsubsection{Limitations of Optimizing Attention}

Attention (\autoref{eqn:attention-math}) utilizes the $\softmax$ operation to create a probability distribution of the tokens in embedding space. However, taking the exponent of the values in the $QK^T$ results in values that far exceed the range of even 32-bit floating point numbers. To execute on real machinery, a safer version of softmax (\autoref{eqn:attention-math-safe}) is used that normalizes the elements by subtracting the row's maximum, such that the range of the exponentiation rests between 0 and 1. As maximum and accumulation are both reductions, and the denominator's accumulation is dependent on the maximum computation, the loop fusion is impossible for the compiler to perform automatically.


Loop tiling is the transformation that allows us to partition the loop to obtain a subtile that can be transformed into a dispatch to the GPU. However, if we are unable to fuse the loop, each loop must be tiled separately, resulting in multiple dispatch calls which is inefficient. Fortunately, by applying the online softmax transformation as described in \cite{milakovOnlineNormalizerCalculation2018}, we are able to derive a single nested loop as in \autoref{alg:online-attention}. Not only is this loop tileable, it also allows the programmer to automatically derive the same kernel as devised in Flash Attention 2 \cite{daoFlashAttention2FasterAttention2023}. Unlike Flash Attention, which is written as a low-level Triton kernel, our attention implementation is written as a high-level neural network. This allows us to perform subsequent tiling and optimizations on the attention mechanism such as quantization, conversion to MXFP \cite{rouhaniMicroscalingDataFormats2023} formats and other low-level optimizations, while still retaining the high-level representation.

\subsection{Compiling to Accelerate Block-Sparse Linear Algebra with Raytracing Hardware}

Target Venue: ASPLOS 2026 Summer Cycle (August 2026) \\
Backup Deadline: PLDI 2027 (est. November 2026)

General purpose GPU computing has its origins as a repurposing of the raster pipeline \cite{bolzSparseMatrixSolvers2003,krugerLinearAlgebraOperators2003}, resulting in the pipeline's subsequent generalization and abstraction that culminated in the current year's compute pipeline of launch grids and thread blocks. However, when adapting the general pipeline for raytracing, the limitations of compute were laid clear: as a SIMD architecture, performance would degrade quickly due to the heavy branching and recursion present in raytraced workflows. Thus, the raytracing pipeline (\autoref{fig:raytracepipe}) was introduced, with the ability to reorganize threads \cite{adinetCUDADynamicParallelism2014}, to loop back to previous stages and built-in acceleration of the bounding volume hierarchy traversal. In an attempt to coax lightning into striking twice, work began immediately on utilizing the pipeline for non-geometric workflows. While many of these attempts were successful \cite{menesesAcceleratingRangeMinimum2024,bauerVisibilityAlgorithmsDynamic2023,haGeneralizingRayTracing2024,Evangelou2021RadiusSearch,zhangMLIRLinalgDialect2022,hennebergRTIndeXExploitingHardwareAccelerated2023}, reformulating the algorithm as a geometric problem and separating the program into the components of a raytracing pass requires low-level, domain-specific knowledge of manipulating graphics pipelines and resources. There currently exists no abstraction that maps to the utilization of the raytracing pipeline as perfectly nested loops do for the tiling of the compute pipeline.

\subsubsection{Abstraction candidates} The natural candidate for abstraction is \emph{sparse linear algebra}. The art of treating linear algebra programs like geometric problems is not new; polyhedral computations treat the iteration space and tensors as integer polyhedra \cite{grosserPolyhedralASTGeneration2015}. Likewise, the row and column indices of sparse linear algebra could be treated as coordinates in geometric space, and retrieving all sparse elements in a row could be done with a raycast along the row's index. Zhang et al. \cite{zhangRTSpMSpMHarnessingRay2025} devised an algorithm to accelerate sparse matrix-sparse matrix multiplication with raytracing. By specifying the lowering of certain sparse operators to be optimized for RT cores, there is reason to hypothesize that more complex programs could be fused into the subsequent kernels to yield performant GPU-accelerated code. Additionally, block-sparse data structures exist as quads in geometric space, which reduces the number of elements in the BVH, while also taking advantage of the GPU's SIMD architecture thanks to spatial locality.

\paragraph{Hash} A common pattern across the various raytrace-targeted formulations of non-geometric problems is the \emph{hash}ing of the stored elements into a tuple of nine $\mathsf{float32}$ elements. This arises due to the ray-traced pipeline's acceleration structures that are fixed to storing three-dimensional geometry, however, hashing itself is inherent to some of these programs as well.

Taichi \cite{huTaichiLanguageHighperformance2019} is a high-performance user-schedulable language that separates computation from data structures. Computations are always written as if accessing a dense structure, while a separate schedule designates the layout of the data being accessed. Data structures are devised with three structural nodes: \emph{dense} arrays, \emph{dynamic} arrays and crucially, \emph{hash}, lending credence to hash's candidacy as a stand-in for raytrace-accelerated access.

Lastly, if the hash were specified to be \emph{order-preserving}, the accompanying bounding volume hierarchy would be able to take advantage of this feature to cull early in the recursion process.

% gather? openmp?

\subsubsection{The Future of Ray-traced Accelerators} As current raytracing cores are heavily optimized towards solving the graphics problem, Barnes et. al propose a more generic accelerator, the Hierarchical Search Unit \cite{barnesExtendingGPURayTracing2024}, to abstract the programming model for general purpose. Issues with the current raytracing cores presented are the inability to handle more than three dimensions and the lack of visibility over the BVH data structures.

\subsubsection{Criteria for Success} Achieving an abstraction that lowers to ray-traced acceleration as efficiently as tensor computations do for tiled computation would be a massive success. We have collected a suite of sparse problems that form the state-of-the-art of raytrace-accelerated programs, and achieving comparative performance to any of these approaches would prove our abstraction useful and beneficial to adopt in compiler frameworks.

However, we take a realistic lens based on our prior work on attention tiling, and observe that we targeted a very specific program that was very well understood and already had multiple optimized forms proving the viability of the approach. To take aim at all raytrace-acceleratable programs with a single abstraction might prove too lofty an ambition. In this regard, we believe that optimizing a block-sparse kernel for raytraced-acceleration with tensor fusion remains a viable research story.

\subsection{Automatic End-to-End Optimization of Real-Time Graphics Pipelines}

Target Venue: SIGGRAPH Asia 2027 (June 2027) \\
Backup: SIGGRAPH 2028 (January 2028)

% 1. We are doing optimization of real-time pipelines as program rewrites 
% 2. Tiled deferred is a surprisingly involved operation, as geometry needs to be tiled as well
% 3. We want to optimize for temporal locality when optimizing for real-time performance.

While advances in rendering techniques have pushed the envelope of real-time rendering techniques closer towards realism over the past decade, the state of programming real-time simulation engines has largely remained the same: program the host in C++ and the device in the shader language of the platform. The argument has always been that C++ allows fine-grained control over the low-level semantics, however, given the prominence of Python in the machine learning ecosystem to accelerate machine learning models, we would like to question this hypothesis. We will define a user-schedulable DSL for render pipelines, and allow engineers to use a scheduling language to guide the transformation while still allowing the compiler to greedily fuse and optimize the resulting render pass. This brings all the benefits of user-schedulable languages --- mainly, the separation of concerns between computation and optimization --- to the world of real-time rendering, allowing for more maintainable code and faster iteration by users.

\subsubsection{State-of-the-art} 
The state-of-the-art for high performance computing DSLs in computer graphics is Taichi \cite{huTaichiLanguageHighperformance2019}, a Python-embedded DSL that has its user-schedulable language separate the computation from the data format. Taichi is very performant for its target use case, but it struggles to achieve even cinematic performance of 24 frames per second. We argue that the optimization of the pipeline, performed for many years in real-time simulation engines, and caching of frame-to-frame state is critical to achieving real-time performance.

The state-of-the-art real-time simulation engine for comparison is Unreal Engine 5's Lumen engine \cite{LumenGlobalIllumination}, which adopts many advanced graphics techniques to achieve realistic graphics. Global illumination is achieved by accumulating light data over several frames, known as \emph{temporal sampling} \cite{lambruTemporalSamplingRealTime2021}. As with our machine learning compatriats, beating the hand-tuned equivalent is nigh impossible, but achieving comparable real-time performance alone would be a fantastic result.

\subsubsection{Reactive programming} A key feature of real-time simulation engines that stands out from offline rendering engines is the expectation of temporal locality, resulting in stateful functions executed from frame to frame. The semantics of frame-to-frame state can be captured with an aspect of reactive programming known as \emph{synchronous reactions} \cite{pompougnacWeavingSynchronousReactions2022}.


\subsubsection{Criteria for Success} As control set ups, we have to turn to tutorial projects by LearnOpenGL \cite{vriesJoeyDeVriesLearnOpenGL2025} and Sascha Willems \cite{SaschaWillemsVulkanExamples}, as many graphics engines do not make it easy to isolate features of their graphics pipeline for apples-to-apples comparisons. Success is defined by achieving real-time framerates while applying transformations that further optimize the OpenGL/Vulkan tutorial examples with minimal (<20) lines of code expressed as program transformations.

A groundbreaking success would have occurred if either of the following were achieved: 
\begin{itemize}
  \item We surpass Taichi's performance, achieving cinematic performance in their domain without loss in fidelity or significant increase in code complexity.
  \item We can achieve real-time performance in an apples-to-apples comparison with Unreal Engine 5's Lumen Engine \cite{LumenGlobalIllumination} in fewer lines of code.
\end{itemize}
