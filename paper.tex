\begin{abstract}
It has been about two decades since the raster pipeline of the GPU was first used for general compute, sparking off a worldwide, multi-decade, multi-trillion dollar investment into accelerating linear algebra on hardware initially designed for entertainment. With the advent of artificial intelligence, the majority of the research effort has largely been directed towards generalizing the rendering hardware such that it is more usable by generic compute workflows. In particular, linear algebra stands out as the class of programs that is trivially easy to optimize for the GPU, due to the parallelizability of its underlying algorithms. In lieu of this observation, custom architectures spring up in an attempt to further optimize linear algebra workflows. However, we observe that consumer-grade GPUs across all vendors continue to retain hardware accelerators and pipelines designed specifically for computer graphics, with texture samplers and ray tracing acceleration structures as examples. Such functionality goes largely ignored or unused by the majority of the high performance computing community.

Our thesis is as follows: compiling to optimize a program for the GPU is more than just tiling parallelizable loops generically and instruction selection. We aim to repeat history with GPU architecture, to open up the raytracing pipeline and other aspects of graphics-oriented architecture to a wider class of programs. These pipelines have already been proven to improve performance outside of computer graphics; our goal is to provide a workflow for engineers to invisibly take advantage of these pipelines. We will achieve this by using MLIR's hybrid IR to handle \emph{pipeline semantics} separately from computations, designating specific operations for specialized pipelining and then fusing dependent operations into the resulting kernels.

Surprisingly, there is an existing class of programs that currently utilizes all three pipelines of the GPU. Real-time interactive simulations utilize raytracing to calculate global illumination, the raster pipeline to render the scene, and the compute pipeline for miscelleanous computations such as animation skeleton updates and physics. To demonstrate the flexibility of enabling and optimizing for pipeline semantics, we will attempt to declaratively define and optimize the engine for a real-time interative simulation.

In summary, we will attempt to answer the following research questions:
\begin{itemize}
  \item RQ1: What are the restrictions with regards to optimizing linear algebra programs?
  \item RQ2: What is a suitable abstraction for designating a program to use the raytracing pipeline, such that we can apply tile-and-fuse techniques on the resultant program?
  \item RQ3: Can our abstraction sufficiently describe and optimize a complex program utilizing all GPU pipelines, such that the resulting performance is comparable with the handwritten state-of-the-art? 
\end{itemize}
\end{abstract}

\section{Literature Review}

This literature review will span the three topics that the thesis will cover: the GPU architecture, compilers, and computer graphics.

\subsection{GPU and General Purpose Compute}

\emph{Note: GPU terminology is not standardized and inconsistent across vendors. This section will be using Nvidia's terminology, but where modern features are concerned, similar terminology for the vendor-agnostic Vulkan \cite{vulkanHomeVulkanCross2025} will be mentioned as well.}

\begin{figure}
  \includegraphics[scale=0.5]{GPU Architecture.pdf}
  \caption{A heavily simplified block diagram of Nvidia's GB202 GPU, also known as the RTX 5090 \cite{NVIDIABlackwellArchitecture2025}. \label{fig:gpuarch}}
\end{figure}

The GPU, or graphics processing unit, is a single-instruction multiple-data (or SIMD) architecture that consists of a massive number of streaming multiprocessors (or SMs) \autoref{fig:gpuarch}. A streaming multiprocessor consists of a set of CUDA cores and a set of warp schedulers, and execute bundles of threads known as warps. On Nvidia architectures, an SM receives a warp of 32 threads that share four warp schedulers. % Pre-Volta, threads would conditionally execute the same instruction eight times in parallel four times in sequence for the total of 32 threads. However, as of Volta, each thread has its own program counter, and programmers are encouraged to treat each thread as its own instance in a paradigm known as SIMT (single-instruction multiple-thread). The underlying hardware attempts to retain the performance granted by SIMD by grouping threads with similar control flow, however, if inter-lane control flow diverges too much, they become subject to performance degradation in what is known as \emph{warp divergence}.

Each streaming multiprocessor is also home to a set of \emph{application-specific integrated circuits} for accelerating common functions. Tensor cores allow for fast tensor fused-multiply-and-add across the warp, and ray tracing cores accelerate the triangle-ray intersection operation. Moreover, due the GPU's historic purposes, streaming multiprocessors also have access to \emph{texture mapping units} (TMUs) that accelerate linear and bilinear interpolation of values in the bound texture resource.

\paragraph{Programming for the GPU} To program for the GPU, programmers write what is known as a \emph{kernel}. The kernel is executed over a large number of threads known as a \emph{grid} which is a tuple $(G,B)$ of $G$ thread blocks each containing $B$ threads for a total of $G \cdot B$ threads in a dispatch. Each invocation of the kernel is assigned a block identifier and a thread identifier, allowing the program to branch based on the invocation identifier. Within a block, threads are able to share memory and synchronization primitives, although grid-level synchronization is made available by a driver. On kernel dispatch, each block is issued to a streaming multiprocessor, which then partitions the block into warps for execution. Programmers for Nvidia architectures may use CUDA to write kernels, and for programmers who wish to target a wider variety of hardware, they may write the kernel as a compute shader compiled to SPIR-V and execute it using the Vulkan API.

Typically, a kernel dispatch is performed from the CPU (also known as the host device). However, the ability to dispatch kernels from the GPU grows increasingly supported, reducing the need for ping-pong between the CPU and GPU. In CUDA, the feature is known as \emph{Dynamic Parallelism} \cite{adinetCUDADynamicParallelism2014}, and in Vulkan, the extension is known as \emph{Device-Generated Commands} \cite{VK_EXT_device_generated_commands3VulkanDocumentation}.

\subsection{Compilers for the GPU}

As a massively parallel architecture, compilers for the GPU are closely associated with parallel compilers. Aside from the previously mentioned CUDA and Vulkan, APIs such as OpenCL \cite{stoneOpenCLParallelProgramming2010} allow for parallel programming of heterogeneous hardware. 

Polyhedral compilers \cite{grosserPolyhedralASTGeneration2015,GRAPHITEPolyhedralAnalyses,baghdadiTiramisuPolyhedralCompiler2019} are compilers that operate on perfectly nested affine loops known as static control parts (or SCoPs). By restricting array accesses to affine expressions on loop induction variables, formulas can be derived to calculate statistics about programs such as memory limits, cache locality that can then be optimized for. Moreover, loop transformations can be expressed as affine transformations on the loop induction variations, making polyhedral programs closed under loop transformations and can be recursively optimized. Work has also been done on directly targeting the GPU \cite{verdoolaegePolyhedralParallelCode2013}, by tiling the SCoP and using affine expressions to compute the memory requirement of the subtile being dispatched to the GPU.

\subsubsection{User-schedulable languages} User-schedulable languages \cite{ragan-kelleyHalideDecouplingAlgorithms2017,chenTVMAutomatedEndtoEnd2018, ikarashiExo2Growing2025} refer to programming languages that specify two languages, a declarative language to describe the computation of the program, and a scheduling language to describe the optimization and gradual lowering of the program to the hardware. This achieves separation of concerns when reasoning about the numerics of the computation versus its performance.

\subsubsection{MLIR} LLVM's Multi-Level IR (MLIR) \cite{lattnerMLIRCompilerInfrastructure2020} framework specifies an SSA-driven hybrid IR that organizes high- and low-level semantics into separate \emph{dialects}. This can span from the high-level \dialect{linalg} dialect which specifies perfectly nested loops \cite{LinalgDialectRationale}, the \dialect{tensor} dialect which describes the layout and allocation of dense multidimensional arrays, to the low-level \dialect{SPIR-V} that targets Vulkan compute and \dialect{LLVM} for CPUs. Dialect-agnostic optimizations such as constant subexpression elimination and dead code elimination are implemented and executed by the framework's drivers.

Triton \cite{tilletTritonIntermediateLanguage2019} is an MLIR-based compiler that provides a high-level Python-embedded DSL for specifying tile semantics, which is immediately translated to its own eponymously-named tile-based MLIR dialect. Other machine learning compilers, such as TorchInductor \cite{anselPyTorch2Faster2024}, XLA \cite{XLACompilingMachine}, and IREE \cite{theireeauthorsIREE2019}, aim to consume neural networks as a sequence of computations and each have their own methods of lowering. We will further elaborate on our work in IREE in \autoref{sec:progressreport}.

\subsection{GPU and Processing Graphics}

As we saw with general compute, the GPU has come a long way from being a fixed-function pipeline, manually plugging in transformation matrices and lights to draw to the screen texture. However, the vast majority of consumer grade GPUs are designed for exactly what it is named for: graphics processing. The compute pipeline, while the most general, is far from the only pipeline available on the GPU. In fact, there are two other pipelines dedicated to graphics rendering available:
\begin{itemize}
  \item Raster pipeline
  \item Raytracing pipeline
\end{itemize}

To dispatch work to the GPU and select the appropriate pipelines, render engines interface with the graphics card using low-level APIs such as DirectX \cite{stevewhimsDirect3D12Reference} and Vulkan \cite{vulkanHomeVulkanCross2025}. One common abstraction implemented by graphics engines, such as O3DE \cite{O3DERenderHardware} and NVIDIA-RTX \cite{NVIDIARTXNVRHI2025}, is the \emph{rendering hardware interface}, which reduces the dependency on the choice of API.

\subsubsection{The Raster Pipeline}

The raster pipeline (\autoref{fig:rasterpipe}) is what directs the graphics card to transform vertex buffers through primitives into fragments that get written into the output texture. Vertex, tesselation and geometry shaders are collectively the \emph{geometry} step of the raster pipeline, producing primitives that are then rasterized into fragments that are \emph{shaded} by the fragment shader.

\begin{figure}
\includegraphics[scale=0.45,keepaspectratio]{Raster Pipeline.pdf}
\caption{The raster pipeline.\label{fig:rasterpipe}}  
\end{figure}

\label{sssec:rasterization}

\paragraph{Deferred Shading} As there are far more fragment shader invocations than vertex shader invocations, significant gains are made by not performing expensive lighting computations. Deferred shading defers the lighting computation to a separate render pass, painting the intermediate values required by the rendering equation into a set of output textures known as the geometry buffer (or G-buffer). While this improved the performance of lighting computations, deferred shading was notoriously memory intensive. As an embarrassingly parallel operation, however, the deferred shading computation could be tiled, saving the memory limits of the G-buffer.

\paragraph{Forward+} Forward rendering refers to performing the entire graphics pass, from geometry through to shading, in a single render pass. Forward+ \cite{haradaForwardBringingDeferred2012} takes the tiling of the deferred shading pipeline and applied it to forward rendering, tiling the camera frustum and performing frustum culls of the lights in the scene using a compute shader. The insight drawn from Forward+ was that deferred shading was not the final destination of graphics optimization; the true cost may be memory traffic. 

\paragraph{Post-processing} While the typical graphics pass produces a realistic image of the scene, many applications of real-time graphics are typically geared towards entertainment such as video games. Complete realism may not always be the requirement, and thus, artists may tune the final image, applying \emph{post processing effects} such as depth of field\cite{mcintoshEfficientlySimulatingBokeh2012} and tone mapping \cite{eilertsenRealtimeNoiseawareTone2015} to achieve a desired effect on the viewer. As each of these effects forms, massive performance gains can be made by \emph{fusing} adjacent passes into a single shader, avoiding the materialization of intermediate textures and minimizing the number of draw calls.

\subsubsection{The Raytracing Pipeline}

The raytracing pipeline (\autoref{fig:raytracepipe}) is a different pipeline that graphics programmers can opt to use that is optimized for raytracing workflows. Compared to the rasterization and compute pipelines, the raytracing pipeline allows the program to loop back and generate more shader invocations. Rays are generated by the Ray Generation Shader (RGS), which are then raycast into a hardware-accelerated bounding volume hierarchy (BVH) utilizing the raytracing core ASICs. 

\begin{figure}
\includegraphics[scale=0.55,keepaspectratio]{Raytrace Pipeline.pdf}
\caption{The ray tracing pipeline and its associated acceleration structures (AS). \label{fig:raytracepipe}}  
\end{figure}


\subsubsection{The Rendering Equation}

Ultimately, both render pipelines were designed to solve the render equation \cite{kajiyaRenderingEquation1986}, defined in \autoref{eqn:rendering}, which is the equation used to compute the value of a point's irradiance. The computation is done by integrating over the hemisphere $\Omega$, taking in as input the normal at the point $\mathbf{n}$ and incoming and outgoing radiance $L_i$ and $L_o$ along the directions $\omega_i$ and $\omega_o$ respectively. $f$ most often appears as $f_r$, known as the bidirectional reflection function, which is the proportion of light reflectioned from $\omega_i$ to $\omega_o$.
\begin{align}
  \label{eqn:rendering}
  \int_\Omega L_i(\omega_i)f(\omega_i,\omega_o,\theta)\langle \mathbf{n}, \omega_i \rangle \mathsf{d} \omega_i
\end{align}

The integral over the hemisphere is what allows for computing global illumination in a realistic manner. By nature of being an integral over a 2D manifold, it is also computationally intensive, yet must be performed for every fragment in the render target to achieve realistic lighting. In real-time workflows, radiance probes \cite{silvennoinenRealtimeGlobalIllumination2017} placed throughout the scene collect global illumination. Radiance cascades \cite{RadianceCascadesPaperOut_latexmk2RadianceCascadespdf} are a modern technique that utilize the mipmap feature of TMUs to accelerate the interpolation of irradiance data from adjacent radiance probes.

\subsection{Compilers in Computer Graphics}

Computer graphics as a field is huge, spanning different rendering techniques and the use of machine learning in various parts of the render pipeline. We will hence cover a small subset of it relevant to this PhD, specifically targeting the use of compiler techniques in computer graphics. 

\subsubsection{Domain Specific Languages (DSLs) for Computer Graphics}
A number of DSLs have been devised, some specfically for computer graphics, others for more generic computation. Taichi \cite{huTaichiLanguageHighperformance2019} is a high-performance DSL written for Python that is designed for high performance sparse programs, a class of programs that includes raytraced rendering. LuisaRender \cite{zhengLuisaRenderHighPerformanceRendering2022} and RenderKernel \cite{yangRenderKernelHighlevelProgramming2024} are two attempts at creating a high-level DSL for raster pipelines, attempting to use Python's decorator functionality to specify which pieces of code are kernels to be dispatched to the GPU.

\subsubsection{Inverse Rendering}

Inverse rendering derives geometry and materials from one or more final images of a target scene. This is achieved through machine learning; specifically, the approach of \emph{differentiable rendering} uses \emph{automatic differentiation} (or autodiff) of the shaders to produce geometry and textures that would produce the same target images. State of the art in the field includes Mitsuba (and its underlying IR, DR.JIT \cite{jakobDRJITJustintimeCompiler2022}), which is able to automatically differentiate the whole pipeline and train for both geometry and render simultaneously, and SlangD \cite{bangaruSLANGDFastModular2023}, which performs automatic differentiation at the per-shader level which improves performance but forces geometry and render to be trained separately. Crucially, both papers include performance comparisons with the autodiff in machine learning frameworks such as JAX \cite{frostigCompilingMachineLearning2018} and Enzyme \cite{enzymeadEnzymeCon2023HackableAutodiff2024}. We include this as an interesting exploration of compiler techniques in computer graphics, and a potential research pivot should initial plans go awry.

\section{Progress Report}
\label{sec:progressreport}

To begin research into making a compiler for the GPU, we must first delve into what the state of the art of compilers for the GPU are. After being introduced to MLIR's metainfrastructure by working on IRDL \cite{MLIRIRDLAddedIRDL,fehrIRDLIRDefinition2022}, we then started work on implementing an optimization of the attention mechanism in IREE in the latter half of 2025. 

\subsection{Attention Comprehension: Extensible compiler optimization of attention kernels}

Target venue: OOPSLA

The attention mechanism \cite{vaswaniAttentionAllYou2023} in large language models is a parallel algorithm that gives the transformer the ability to infer context. Optimization of attention for GPUs is a heavily researched topic \cite{daoFlashAttentionFastMemoryEfficient2022,daoFlashAttention2FasterAttention2023,dongFlexAttentionProgramming2024}, but by studying the Flash Attention 2 kernel, we observe that it is actually a tiling of the attention mechanism. The issue arises because at the high level, attention is not trivially tileable.
%
\newcommand{\Attention}{\mathsf{Attention}}
\newcommand{\softmax}{\mathsf{softmax}}
\begin{align}
  \label{eqn:attention}
  \quad \Attention(\mathbf{Q}, \mathbf{K}, \mathbf{V}) 
  &= \softmax(\mathbf{Q} \mathbf{K}^T) \mathbf{V}
  \\
  \label{eqn:attention-math}
  &=\left[
    \cfrac {e^{\mathbf{S}_{i,j}}} 
           {\sum_{n=0}^{N} e^{\mathbf{S}_{i,n}}}
    \right]
    \mathbf{V}
    \qquad \text{ where } \mathbf{S} = \mathbf{Q} \mathbf{K}^T
  \\
  \label{eqn:attention-math-safe}
  &=\left[
      \cfrac {e^{\mathbf{S}_{i,j} - m_i}} 
             {\sum_{n=0}^{N} e^{\mathbf{S}_{i,n} - m_i}}
    \right]
    \mathbf{V}
    \qquad \text{ where } m_i = \max_{i}(\mathbf{S}_i)
\end{align}

The mathematical definition of attention is provided in \autoref{eqn:attention}, which we then expand with the definition of $\softmax$ in \autoref{eqn:attention-math}. However, raising $e$ to the power of values traditionally in the $QK^T$ matrix results in values far beyond the limit of what 32-bit floating point is able to capture. Hence, a safe version of softmax is applied by subtracting the maximum row value from the exponent, which we can see in \autoref{eqn:attention-math-safe}.

This presents us with an issue when it comes to loop fusion. Maximum and accumulation are both reductions, and the result of the maximum operation is used in the accumulation operation. The compiler is unable to perform loop fusion of the two loops depicted in \autoref{alg:attention}.

\begin{figure}
\includegraphics[width=\textwidth, keepaspectratio]{attention-unfusable.png}  
\caption{The pink and blue reductions are unfusable, as the result of the former is used in the latter as shown by the red line.\label{alg:attention}}
\end{figure}

\begin{algorithm}
  \caption{Attention, optimized with online softmax\label{alg:online-attention}}
  \begin{algorithmic}[1]
  \Function{Attention}{
    $Q : \mathbb{R}^{N \times d}$,
    $K : \mathbb{R}^{N \times d}$,
    $V : \mathbb{R}^{N \times d}$}

    \State $S, P : \mathbb{R}^{N \times N} \qquad 
            O : \mathbb{R}^{N \times d} \qquad
            m, \sigma :\mathbb{R}^N$
    \State Initialize $m = (-\infty)^N \quad \sigma = (0)^N$,

    % matmul
    \ForAll {$i,j \in [0,N) \times [0, N)$}  
      \For {$k \in [0, d)$}  
        \State $S_{i,j} := S_{i,j} + Q_{i,k} \cdot K_{j,k}$
      \EndFor
    \EndFor

    % softmax
    \ForAll {$i \in [0,N)$} 
      \For {$j \in [0,N)$} 
        \State $m' := m_i$
        \State $m_i := \text{max}(m_i, S_{i,j})$
        \State $\alpha_i := e^{m' - m_i}$
        \State $P_{i,j} := e^{S_{i,j} - m_i} $
        \State $\ell_i := \alpha_i \ell_i + P_{i,j}$
        \For{$k \in [0,d]$}
        \State $O_{i,k} := O_{i,k} + P_{i,j} \cdot V_{j,k} $
        \EndFor
      \EndFor
    \EndFor

    \ForAll {$i \in [0,N)$} 
      \ForAll {$j \in [0,N)$} 
        \State $O_{i,j} := O_{i,j} / \ell_i$
      \EndFor
    \EndFor

    \Return $O$
  \EndFunction
  \end{algorithmic}
\end{algorithm}

Loop tiling is the transformation that allows us to partition the loop to obtain a subtile that can be transformed into a dispatch to the GPU. However, if we are unable to fuse the loop, each loop must be tiled separately, resulting in multiple dispatch calls which is inefficient. Fortunately, by applying the online softmax transformation as described in \cite{milakovOnlineNormalizerCalculation2018}, we are able to derive a single nested loop as in \autoref{alg:online-attention}. Not only is this loop tileable, it also allows the programmer to automatically derive the same kernel as devised in Flash Attention 2 \cite{daoFlashAttention2FasterAttention2023}. Unlike Flash Attention, which is written as a low-level Triton kernel, our attention implementation is written as a high-level neural network. This allows us to perform subsequent tiling and optimizations on the attention mechanism such as quantization, conversion to MXFP \cite{rouhaniMicroscalingDataFormats2023} formats and other low-level optimizations, while still retaining the high-level representation.

This paper is still a work in progress, as we have not fully integrated the functionality into IREE for a proper benchmark. Once implemented, we will be using the Meta attention gym \cite{MetapytorchAttentiongym2025} to do an apples-to-apples comparison with PyTorch's FlexAttention \cite{dongFlexAttentionProgramming2024}. In terms of timeline, a demo is planned to be presented at CC's C4ML (deadline of December 2025) followed by a submission at OOPSLA in 2026. 

Through the process of writing this paper, we have become familiar with the design of MLIR's Transform dialect \cite{luckeMLIRTransformDialect2024}, its extensions, and how to progressively lower linear algebra operators to the GPU.


\section{Thesis Proposal}

The programmable deliverable of this thesis is to develop an MLIR dialect for dispatching work to the GPU. The research value of such a project is not immediately apparent, however, it does lay the groundwork and an overarching research theme for research ideas exploring cross-pipeline optimizations. In the short term, the concrete paper ideas are:
\begin{itemize}
  \item Compiling to Accelerate Block-Sparse Linear Algebra with Raytracing Hardware
  \item Raster Pipeline Optimizations as Program Rewrites
\end{itemize}

\subsection{Compiling to Accelerate Block-Sparse Linear Algebra with Raytracing Hardware}

Target Venue: ASPLOS 

The general idea of tackling linear algebra as a geometry problem is not a particularly novel innovation. Why, even dense GEMM is often modelled as a polyhedral program. Therefore, the idea of modelling sparse-sparse matrix multiplication as a geometric problem should not come as a surprise either. By converting the elements of sparse matrices into triangles and utilizing the ray tracing pipeline's acceleration structure, Zhang et al. \cite{zhangRTSpMSpMHarnessingRay2025} manage to harness the ray tracing hardware to optimize the sparse linear algebra problem, achieving a 1.85x speedup over cuSPARSE.

We observe that Zhang's approach uses OptiX, Nvidia's SDK for ray tracing, and posit that their approach can still be further refined by treating the lowering of the sparse computation to the raytracing pipeline as a compiler optimization. We will attempt to use compiler techniques to not only simplify the writing of the dispatch for the frontend programmer, but also enable well-known optimizations such as block-sparse formats. The block semantics available to block-sparse matrices more easily permit tensor core acceleration, and as geometric primitives with larger volume, should be more efficiently handled by the bounding volume acceleration structures. This approach is clearly cross-pipeline, utilizing both the compute and raytracing pipelines to optimize a linear algebra problem, and is simple to implement and explore with existing tools, allowing us to dedicate engineering effort to building a well-rounded GPU dispatch framework.

\subsection{Raster Pipeline Optimizations as Program Rewrites}

Target Venue: SIGGRAPH / SIGGRAPH ASIA

The raster pipeline is a well-understood programming model utilized by graphics engineers all across the video game industry. One of the most crucial optimizations one could perform to their graphics pipeline is to reduce the amount of overdraw in the scene, and a common way of doing this is with deferred shading. As stated in \autoref{sssec:rasterization}, deferred shading reduces overdraw by only performing the expensive lighting computations on fragments that are actually visible on the screen, but comes at the cost of maintaining a memory-intensive G-buffer. To mitigate the memory overhead, the deferred shading operation may be tiled, not unlike that of the machine learning counterparts.

Hence, we treat the tiling of the render pass as a program rewrite. Unlike linear algebra workloads, the iteration domain is not the only tiling target. The draw command's viewport and the frustum corresponding to the projection matrix must be tiled as well, respectively corresponding to a change in pipeline and geometric semantics. By subdividing and rotating the camera frustum, however, the inter-tile depth buffer becomes incoherent, resulting in non-trivial adjustment for use in post-processing passes that rely on the depth buffer. One example of such a pass is depth-based edge detection. We will investigate the effects of tiling on the geometric semantics of the render pass, and attempt to resolve it with whole program optimization that is only possible with multi-level compilers. This will allow us to investigate the use of compiler rewrites as a means to optimize pipelines.

\subsection{Criteria for Success}

RQ1 will be addressed by the raytracing paper, as we apply compiler techniques to not only apply the raytracing pipeline to sparse linear algebra, but fuse adjacent computations into the loop as well. Success will be determined by how our compiler-based solution holds up against the state of the art sparse linear algebra libraries such as cuSPARSE \cite{CuSPARSE}, MAGMA \cite{abdelfattahMAGMAEnablingExascale2024}, and RTSpMSpM \cite{zhangRTSpMSpMHarnessingRay2025}, comparing the metrics of performance, maintainability and GPU utilization.

As for RQ2, the raster rewrite paper will only partially answer it. As rendering engines are immensely complex and configurable engines, there are far too many intricate details to handle. Hence, we will benchmark our prototype graphics engine against tutorial projects by LearnOpenGL \cite{vriesJoeyDeVriesLearnOpenGL2025} and Sascha Willems \cite{SaschaWillemsVulkanExamples}, which implement deferred shading and other techniques atomically to form a more stable control. If this first paper proves successful, implementing advanced techniques such as radiance cascades or those found Unreal Engine 5's Lumen \cite{LumenGlobalIllumination} will allow us to verify the claim that program rewrites can yield an effective, maintainable codebase for a render engine with comparable performance to the state of the art.
