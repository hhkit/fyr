\begin{abstract}
It has been about two decades since the raster pipeline of the GPU was first used for general compute, sparking off a worldwide, multi-decade, multi-trillion dollar investment into accelerating linear algebra on hardware initially designed for entertainment. With the advent of artificial intelligence, the research effort has been funnelled into generalizing the rendering hardware such that it is more usable by generic compute workflows. In particular, linear algebra stands out as the class of programs that is trivially easy to optimize for the GPU, due to the parallelizability of its underlying algorithms. In lieu of this observation, custom architectures spring up in an attempt to further optimize linear algebra workflows. However, we observe that consumer-grade GPUs across all vendors continue to retain hardware accelerators and pipelines designed specifically for computer graphics, with texture samplers and ray tracing acceleration structures as examples. Such functionality goes largely ignored or unused by the majority of the high performance computing community.

The thesis is as follows: compiling to optimize a program for the GPU is more than just tiling parallelizable loops generically and instruction selection. We aim to open up the raytracing pipeline and other aspects of graphics-oriented architecture to a wider class of programs. These pipelines have already been proven to improve performance outside of computer graphics; our goal is to provide a workflow for engineers to invisibly take advantage of these pipelines without needing to understand the underlying hardware architecture. Existing work in ML compilers exclusively utilize the compute pipeline due to its flexibility and ease-of-tiling, and so, we will account for pipeline semantics by targeting specific high-level operations that can be raytrace-accelerated and greedily fusing dependent kernels into them.

To test the robustness of our approach, we will attempt to use the tools we developed for machine learning programs to implement another existing class of programs that utilizes all three pipelines of the GPU: real-time simulations. Real-time simulations utilize raytracing to calculate global illumination, the raster pipeline to render the scene, and the compute pipeline as a catch-all pipeline for on-chip computations such as animation skeleton updates and physics. That is, we will attempt to define a real-time simulation engine declaratively, then apply guided and automatic compiler rewrites to optimize it such that it achieves real-time performance.

The overarching theme of this thesis is to master utilization of the GPU through compilers. To achieve this mastery, we will attempt to answer the following research questions:
\begin{itemize}
  \item RQ1: What are the restrictions that automatic optimization of linear algebra programs faces?
  \item RQ2: What is a suitable abstraction for designating parts of a program to use the raytracing pipeline, such that we can apply compiler techniques to achieve a performant program that fully utilizes all capabilities of the GPU?
  \item RQ3: Can program rewrites reduce the performance gap between raytraced and rasterized workflows in real-time scenarios? 
\end{itemize}
\end{abstract}

\section{Background and Literature Review}

This section will span the three topics that the thesis will cover: the GPU architecture, compilers, and computer graphics.

\subsection{GPU and General Purpose Compute}

\emph{Note: GPU terminology is not standardized and inconsistent across vendors. This section will be using Nvidia's terminology, but where modern features are concerned, similar terminology for the vendor-agnostic Vulkan \cite{vulkanHomeVulkanCross2025} will be mentioned as well.}

\begin{figure}
  \includegraphics[scale=0.5]{GPUArchitecture.pdf}
  \caption{A heavily simplified block diagram of Nvidia's GB202 GPU, also known as the RTX 5090 \cite{nvidiaNVIDIARTXBlackwell2025}. \label{fig:gpuarch}}
\end{figure}

The GPU, or graphics processing unit, is a single-instruction multiple-data (SIMD) architecture (\autoref{fig:gpuarch}) that consists of a massive number of streaming multiprocessors (SMs). Each SM consists of a set of CUDA cores and a set of warp schedulers, and execute bundles of threads known as warps. On Nvidia architectures, warps contain 32 threads. % Pre-Volta, threads would conditionally execute the same instruction eight times in parallel four times in sequence for the total of 32 threads. However, as of Volta, each thread has its own program counter, and programmers are encouraged to treat each thread as its own instance in a paradigm known as SIMT (single-instruction multiple-thread). The underlying hardware attempts to retain the performance granted by SIMD by grouping threads with similar control flow, however, if inter-lane control flow diverges too much, they become subject to performance degradation in what is known as \emph{warp divergence}.

Each SM also contains dedicated circuitry for accelerating common functions. Tensor cores allow for fast tensor fused-multiply-and-add across the warp, and ray tracing cores accelerate the triangle-ray intersection operation. Moreover, due the GPU's historic purposes, SMs also have access to \emph{texture mapping units} (TMUs) that accelerate multilinear interpolation of values in the bound texture resource.

\paragraph{Programming for the GPU} \emph{Kernel} is the common term to refer to the part of the program that executes on the GPU. Programmers for Nvidia architectures may use CUDA to write kernels, and for programmers who wish to target a wider variety of hardware, they may write the kernel as a compute shader compiled to SPIR-V and execute it using the Vulkan API. The kernel is executed over a large number of threads known as a \emph{grid}, which consists of $G$ blocks each containing $B$ threads. Each invocation of the kernel is assigned a block identifier and a thread identifier, allowing the program to branch based on the invocation identifier. Within a block, threads are able to share memory and synchronization primitives, although grid-level synchronization is made available by a driver. On kernel dispatch, each block is issued to a streaming multiprocessor, which then partitions the block into warps for execution. 

Typically, a kernel dispatch is performed from the CPU (also known as the host device). However, the ability to dispatch kernels from the GPU grows increasingly supported, reducing the need for ping-pong between the CPU and GPU. This feature is known as \emph{Dynamic Parallelism} \cite{adinetCUDADynamicParallelism2014} in CUDA and \emph{Device-Generated Commands} \cite{blumenkrantzVK_EXT_device_generated_commands3VulkanDocumentation2024} in Vulkan.

\subsection{Compilers for the GPU}

As a massively parallel architecture, compilers for the GPU are closely associated with parallel compilers. We introduce a model for discussing loop semantics which we will use to discuss the existing work in the field.

\subsubsection{Loop optimizations} Loop optimizations are a set of program transformations that target loops; specifically, they target \emph{perfectly nested loops}. Perfectly nested loops are defined as loops that nest within each other without statements in between loop headers. They are crucial for loop optimization, as by having no statements in between loop headers, the loop can be compactly represented as a 2-tuple of its iteration domain $\domain \in \mathcal{P}(\mathbb{Z}^{n})$ and its body $S \in \domain \to \mathcal{D}_S$, and transformations can be made to either component without reasoning about the other. We demonstrate this with a C code snippet, but also present a corresponding mathematical notation to simply the syntax and emphasize changes effected by loop transformations. For loops deemed to be embarrassingly parallel, we shall denote them with $\mathbf{for~all}$ instead of $\mathbf{for}$.

\begin{tabular}{p{0.46\textwidth}p{0.46\textwidth}}
\begin{minted}{cpp}
#pragma omp parallel 
for (int i = 0; i < 1024; ++i)
    for (int j = 0; j < 32; ++j)
S:      c[i] = c[i] - a[i][j];
\end{minted}
&%

\begin{algorithmic}
  \State $\mathsf{let }~ \lBrack  S \rBrack (i,j) \triangleq \left( c_i := c_i - a_{i,j} \right) ~\mathsf{in}$ 
  \ForAll {$i \in [0,1024)$}  
    \For {$j \in [0, 32)$}  
      \State $ \lBrack  S \rBrack (i,j) $
    \EndFor
  \EndFor
\end{algorithmic}
\vfill
\end{tabular}

As in many loop optimization models \cite{xueUnimodularTransformationsNonperfectly1997,grosserPolyhedralASTGeneration2015,chenCHiLLFrameworkComposing2008}, we will assume the program iterates through $\domain$ lexicographically. The specific invocation of a statement $S$ executed with induction variables $v \in \domain$ is denoted as $S_{v}$, and the set of all statement invocations as $\mathcal{D}_S$.  The dependency relation $\mathbf{D}_r : \mathcal{D}_S \times \mathcal{D}_S $ defines a partial order on the statement invocations that must be fulfilled to preserve the semantics of the executing program, and may be derived with program analysis \cite{banerjeeSingleLoops1997}.

Above, we may deduce the $i$ loop to be parallel as the reduction variable $c_i$ is local to each $i$ iteration. But the reducing $j$ loop is not parallel, as subtraction is not associative. We encode the dependency relation as $\mathbf{D}_r = \left \{ (S_{i,j}, S_{i,j'}) \mid j < j' \right \}$.

We now define a loop transformation $T: \domain \to \domain$ as a transformation of a loop's iteration domain. For $T$ to be a legal transformation, it must preserve program semantics, which requires the dependency relation to remain satisfied under $T$ (i.e. $\forall (S_u,S_v) \in \mathbf{D}_r . T(u) \prec_{lex} T(v)$).

Consider the transformation 
$R_j := \begin{bmatrix}
    i, j
  \end{bmatrix}
  \mapsto 
  \begin{bmatrix}
    i, 31 - j
  \end{bmatrix}$, which reverses the $j$ loop. 

\begin{tabular}{m{0.275\textwidth}m{0.02\textwidth}m{0.55\textwidth}} \\
\multicolumn{3}{p{0.9\textwidth}}{
  $\mathsf{let }~ \lBrack  S \rBrack (i,j) \triangleq \left( c_i := c_i - a_{i,j} \right) ~\mathsf{in}$ 
}
\\
\begin{algorithmic}
  \ForAll {$i \in [0,1024)$}  
    \For {$j \in [0, 32)$}  
      \State $ \lBrack  S \rBrack (i,j) $
    \EndFor
  \EndFor
\end{algorithmic}
&
$\xrightarrow{R_j}$
&
\begin{algorithmic}
  \ForAll {$i \in [0,1024)$}  
    \For {$j \in [0, 32)$}  
      \State $ \lBrack  S \rBrack (i,31-j) $
    \EndFor
  \EndFor
\end{algorithmic}
\end{tabular}

In the initial loop, $(S_{0,0}, S_{0,1}) \in \mathbf{D}_r$. However, $R_j([0,0]) \not\prec_{lex} R_j([0,1])$ (i.e $[0,31] \not\prec_{lex} [0,30]$). Hence, the transformation $R_j$ does not fulfill the dependency relation $\mathbf{D}_r$ and is thus illegal.

While there are a myriad of loop transformations such as loop reversal, loop skewing, and loop unrolling, we will focus on the two transformations that are required in any loop optimizing framework targeting the GPU: \emph{loop tiling} \cite{xueTilingLoopTransformation2011,wonnacottScalabilityLoopTiling2013} and \emph{loop fusion} \cite{manjikianFusionLoopsParallelism1997, darteComplexityLoopFusion1999,qiaoLoopFusionKernel2019,mehtaRevisitingLoopFusion2014}. 

\paragraph{Loop tiling} Loop tiling splits a loop dimension into multiple smaller dimensions. Tiling is a crucial transformation as perfectly nested loops are \emph{closed} under tiling, allowing the inner loops to be extracted as kernels \cite{wonnacottScalabilityLoopTiling2013} and be further tiled for lower-level optimizations such as vectorization.

\begin{tabular}{m{0.275\textwidth}m{0.08\textwidth}m{0.55\textwidth}} \\
\multicolumn{3}{p{0.9\textwidth}}{

}
\\
\begin{algorithmic}
  \ForAll {$i \in [0,1024)$}  
      \State $\lBrack  S \rBrack (i)$
  \EndFor
\end{algorithmic}
&
$\xrightarrow{\mathsf{tile}(16)}$
&
\begin{algorithmic}
  \ForAll {$i \in [0,64)$}  
    \ForAll {$i' \in [0,16)$}  
      \State $\lBrack  S \rBrack (16i + i')$
    \EndFor
  \EndFor
\end{algorithmic}
\end{tabular}
\paragraph{Loop fusion} Loop fusion refers to the fusion of dependent loops to reduce the cost of iteration, remove intermediate values, or, when combined with tiling, enable the extraction of more complex kernels. We demonstrate this by fusing a transpose into a matrix multiplication --- a common fusion that exploits cache locality.

\begin{tabular}{m{0.375\textwidth}m{0.08\textwidth}m{0.55\textwidth}} \\

\subsubsection{Polyhedral compilers}  Polyhedral compilers \cite{grosserPolyhedralASTGeneration2015,popGRAPHITEPolyhedralAnalyses2006,baghdadiTiramisuPolyhedralCompiler2019,bondhugula2008pluto} operate on perfectly nested loops that are restricted to having loop bounds that are Presburger expressions over the upper loops' induction variables \cite{feautrier1988parametric}. If all memory accesses within the statement are also Presburger expressions on the loops' induction variables, the programs are known as static control parts (or SCoPs). As an abstract model of the program, the polyhedral representation of a SCoP is an exact approximation.

Affine expressions may be derived to derive heuristics such as memory usage \cite{quillere2000optimizing} and cache locality \cite{pitchanathanFalconScalableAnalytical2024, zinenko2017unified}. We may also derive these expressions about the subtile of a perfectly nested loop, allowing us to extract a memory-optimal tile as a kernel to dispatch to the GPU as in PPCG \cite{verdoolaegePolyhedralParallelCode2013}.

\subsubsection{User-schedulable languages} User-schedulable languages \cite{visserStrategoLanguageProgram2001, ragan-kelleyHalideDecouplingAlgorithms2017,chenTVMAutomatedEndtoEnd2018, ikarashiExo2Growing2025} are programming languages that specify two languages, a declarative language to describe the computation of the program, and a scheduling language to describe the optimization and gradual lowering of the program to the hardware. This achieves separation of concerns when reasoning about the numerics of the computation versus its performance.

\subsubsection{Hybrid IR: SSA and Regions} LLVM's MLIR \cite{lattnerMLIRCompilerInfrastructure2020} framework specifies an SSA-driven hybrid IR that organizes high- and low-level semantics into separate \emph{dialects}. In MLIR, operations may have regions that contain basic blocks that contain operations, allowing for operations of different dialects to coexist in the same program.

We highlight the following dialects which we regularly use in our work:
\begin{itemize} 
  \item \dialect{tensor}: High-level types and operations for $N$-dimensional shaped arrays
  \item \dialect{linalg} \cite{thellvmfoundationLinalgDialectMLIR2025}: Perfectly nested loops operating on shaped values (\dialect{tensor}s, \dialect{memref}s, etc.)
  \item \dialect{spirv}: Low-level IR targeting GPU code generation using Vulkan's SPIR-V \cite{khronosSPIRVSpecification2025}
  \item \dialect{llvm}: Low-level IR that can be optimized by the LLVM \cite{lattnerLLVMCompilationFramework2004} backend.
  \item \dialect{transform} \cite{luckeMLIRTransformDialect2024}: MLIR's scheduling language for program transformations 
\end{itemize}

Triton \cite{tilletTritonIntermediateLanguage2019} is an MLIR-based compiler that provides a high-level Python-embedded DSL for specifying tile semantics, which is immediately translated to its own eponymous tile-based MLIR dialect. Other machine learning compilers \cite{anselPyTorch2Faster2024, sabneXLACompilingMachine2020, theireeauthorsIREE2019} represent neural networks as a high-level IR, and each have their own methods of lowering to the corresponding hardware. 

\subsection{Neural Networks}

This section will discuss several types of neural networks (or neural nets) and the various high-level operators that occur in these programs.

\subsubsection{Feed-forward neural networks} The simplest neural network is a feed-forward neural network, where information always flows from inputs to outputs. We demonstrate how a neural network may be represented as a matrix multiplication:

\centerline{
\includegraphics[scale=1.15]{i-hate-ml.drawio.pdf}
}

To reduce the linearity of the matmul's result, each output element $y_n$ may be element-wise passed into an activation function $f_a$, of which the most commonly used are $\mathsf{sigmoid}$ and $\mathsf{ReLU}$.

To train for the correct weight values, the error of the results are passed into a cost function, after which the whole network is \emph{differentiated} to obtain the vector of weight adjustments. Propagating the errors back into the weight tensor is known as \emph{backprogation} or \emph{gradient descent}. As new activation functions or new network designs are devised with different layers, calculating the gradient of the program grows more complex and difficult to maintain. Automatic differentiation (\emph{autodiff}) \cite{enzymeadEnzymeCon2023HackableAutodiff2024,jakobDRJITJustintimeCompiler2022,thejaxauthorsAutomaticDifferentiationJAX2024,paszkeAutomaticDifferentiationPyTorch2017,rall1996introduction,bangaruSLANGDFastModular2023} exists in machine learning compilers to remove the burden of differentiation from their users as they iterate through different network designs.

\subsubsection{Convolutional neural networks} Convolutional neural networks \cite{osheaIntroductionConvolutionalNeural2015} (CNNs) are neural nets that target the field of pattern recognition in images. The three layers involved in a CNN are:
\begin{itemize}
  \item Convolution layer % feature extraction 
  \item Pooling layer % downsamping 
  \item Fully-connected layer % dense layers
\end{itemize}

\paragraph{The Convolution Layer: Stencil computation} The convolution layers extract features from or reduce noise in the input, extracting values for the fully-connected layer to train on.  A fixed pattern (i.e. the stencil) is applied to each element of an array, drawing data from adjacent neighbors. We demonstrate this using the $3\times3$ horizontal stencil of the Sobel filter \cite{sobelIsotropic3x3Image2014}, an early edge detector.

\includegraphics[scale=1.4]{convolution-anno.pdf}

We observe that elements at the boundaries of the image do not have neighbors beyond the boundary for the stencil to apply to, and so the policy for handling this edge case is known as the computation's \emph{boundary condition} (BC). In the case of Sobel, the BC is to take the element itself, though other policies may include using 0 or wrapping around the image.

The computation of each element of the stencil computation is embarrassingly parallel \cite{maruyamaPhysisImplicitlyParallel2011} and, hence, stencil computations are a classical target for tiling \cite{bandishtiTilingStencilComputations2012,hagedorn2016extension}. When tiling a stencil computation, the required neighbors must also be fetched into memory. The set of neighbors that participate in the computation but are not updated by the tile is known as the \emph{halo region} \cite{holewinskiHighperformanceCodeGeneration2012}. Stencil computations may be represented as polyhedral loops, and many stencil computations can be found in polyhedral benchmark test suites \cite{pouchetPolyBench2010}.

\paragraph{Pooling layer} CNNs do not require pixel-perfect information, and may introduce pooling layers to downsample the convolution layer's outputs to reduce the size of the input and prevent overfitting. The most common pooling policies are max pooling (MaxPool) and average pooling (AvgPool) \cite{pmlr-v51-lee16a}.

\paragraph{Fully-connected layer} The fully-connected layer is simply a feed-forward neural network.

  \caption{The transformer architecture \cite{vaswaniAttentionAllYou2023} as depicted by Godoy \cite{godoyDvgodoyDlvisuals2025} (CC BY). \label{fig:transformer}}
\end{figure}

In transformers, inputs and outputs are not normally provided in numeric form. Language, for instance, tends to arrive in text and tokenized strings. These tokens are mapped to vectors via an \emph{embedding} function (or an \emph{encoder}/\emph{decoder}). Unlike convolutional neural networks, transformers will also encode the position of a token into the embedding vector as well.

\paragraph{Attention} The mechanism present throughout the transformer architecture is the attention mechanism (\autoref{eqn:attention-masked}, \cite{vaswaniAttentionAllYou2023}), which is able to dynamically determine the value of context.

\begin{equation}
  \Attention_{\mathbf{M}}(\mathbf{Q}, \mathbf{K}, \mathbf{V}) = \softmax(\mathbf{Q} \mathbf{K}^T - \mathbf{M}) \mathbf{V}
  \label{eqn:attention-masked}
\end{equation}

The \emph{query} vector $\mathbf{Q}$ represents a query about the token and the \emph{key} vector $\mathbf{K}$ represents an answer to the query. For example, in language, adjectives modify the meaning of nouns that follow it, so $\mathbf{Q}$ would contain higher values where the nouns might expect adjectives, and $\mathbf{K}$ might contain the adjectives themselves. The computation $\mathbf{S}=\mathbf{Q}\mathbf{K}^T$ polls the questions against the answers, forming the \emph{context} of the attention kernel. Sometimes, a value in the context requires discarding (for instance, causal masking prevents earlier tokens from influencing later tokens) by subtracting $\inf$ from the values --- this is represented by the $\mathbf{M}$ matrix. The context, post normalization with $\softmax$, is then applied to the inputs once again by being multiplied with the value matrix $\mathbf{V}$.

Being at the core of the transformer architecture, the optimization and parallelization of attention has been the topic of many a machine learning research paper. Flash Attention and its variants \cite{daoFlashAttentionFastMemoryEfficient2022,daoFlashAttention2FasterAttention2023} present a manual tiling of the attention mechanism for the respective GPUs at the time of publication. Compiler engines such as FlexAttention \cite{dongFlexAttentionProgramming2024} and FlashInfer \cite{yeFlashInferEfficientCustomizable2025} aim to provide a configurable template for the various attention variants developed \cite{liuRingAttentionBlockwise2023,brandonStripedAttentionFaster2023,kwon2023efficient}.

\subsubsection{Neural Network Formats} Each machine learning framework has its own exchange format to import and export, allowing weights and programs to be shared between researchers and execution environments. For instance, TensorFlow~\cite{tensorflow2015-whitepaper} uses Keras~\cite{chollet2015keras} and PyTorch~\cite{paszkePyTorchImperativeStyle2019} uses Python's built-in serializer, although each framework may also support the formats of others. To reduce fragmentation in the ecosystem, several open formats have been developed and proposed, amongst which include Open Neural Network eXchange (ONNX~\cite{onnxruntime}) format and the Neural Network Exchange Format (NNEF~\cite{khronosNNEFNeuralNetwork2016}).

\subsection{GPU and Processing Graphics}

As with general compute, computing on the GPU has come a long way from being a fixed-function pipeline, manually plugging in transformation matrices and lights to draw to the screen texture \cite{segalOpenGLTMGraphicsSystem1994}. However, while data center GPUs \cite{nvidiaNVIDIABlackwellArchitecture2025} have discarded their graphical capabilities to further accelerate block \cite{rouhaniMicroscalingDataFormats2023} and tensor \cite{markidisNVIDIATensorCore2018} operations, consumer grade GPUs retain their historic purpose: graphics processing. In other words, the compute pipeline, while the most general, is not the only way to dispatch work to the GPU. In fact, there are two more pipelines (\autoref{fig:pipelines}):
\begin{itemize}
  \item Raster pipeline
  \item Raytracing pipeline
\end{itemize}

The term for non-host programs in high-performance computing is \emph{kernel}, but in computer graphics, the code that executes in the programmable stages of a pipeline is instead called a \emph{shader}.

To select the appropriate pipelines for computation, render engines interface with the graphics card using low-level APIs such as DirectX \cite{microsoftDirect3D12Reference2021}, Metal \cite{appleinc.MetalOverview2025}, and Vulkan \cite{vulkanHomeVulkanCross2025}. To abstract access to the underlying APIs, graphics engines define a common interface known as the \emph{rendering hardware interface} (RHI) \cite{open3denginecontributorsO3DERenderHardware2025,nvidiaNVIDIARTXNVRHI2025}, which allows for multi-API targeting.

\subsubsection{The Raster Pipeline}

The raster pipeline (\autoref{fig:rasterpipe}) is the primary pipeline, and can be partitioned into two general steps: the \emph{geometry} stage and the \emph{fragment} stage. In the geometry stage, programmers turn input buffers into triangle primitives by specifying either the \emph{vertex}-\emph{tesselation}-\emph{geometry} sequence of shaders, or by a single \emph{mesh shader} in more modern hardware. The hardware then determines which texture elements (\emph{texel}s) in the output texture are inside the triangle (referred to as \emph{rasterization}), then invokes the \emph{fragment shader} on each texel in the fragment stage. As there are far more fragment shader invocations than geometry-stage shaders --- a roughly 3:N relationship --- significant performance gains are more likely to be made by optimizing fragment shaders or culling the number of fragment shader invocations.

\paragraph{Deferred Shading} Deferred shading defers the lighting computation to a separate render pass, painting the intermediate values required by the rendering equation \cite{kajiyaRenderingEquation1986} into a set of output textures known as the geometry buffer (or G-buffer). While this improved the performance of lighting computations, deferred shading was notoriously memory intensive.

The true insight drawn from Forward+ was that deferred shading was not a one-size-fits-all optimization technique; a mixture of factors including memory traffic and overdraw needed to be considered when optimizing a graphics pipeline.

\paragraph{Post-processing} While the typical graphics pass produces a realistic image of the scene, many applications of real-time graphics are typically geared towards entertainment such as video games. Complete realism may not always be the requirement, and thus, artists may tune the final image, applying \emph{post processing effects} such as depth-of-field \cite{mcintoshEfficientlySimulatingBokeh2012} and tone mapping \cite{eilertsenRealtimeNoiseawareTone2015} to achieve a desired effect. Effects such as depth-based edge detection \cite{abidhasanDepthEdgeDetection2016} may also draw on information from the G-buffer. As each of these effects forms, massive performance gains can be made by \emph{fusing} adjacent passes into a single shader, avoiding the materialization of intermediate textures and minimizing the number of draw calls.

\subsubsection{The Raytracing Pipeline}

The raytracing pipeline (\autoref{fig:raytracepipe}) is a different pipeline that graphics programmers can opt to use that is optimized for raytracing workflows. Rays are generated by the Ray Generation Shader (RGS), which are then raycast into a hardware-accelerated bounding volume hierarchy (BVH) utilizing the RT cores. The standout features of the raytracing pipeline are the hardware accelerated raycasts, which are non-programmable, and the option to loop back to a previous stage of the pipeline without another draw call.

\subsection{Compilers in Computer Graphics}

Computer graphics as a field is huge, spanning different rendering techniques and the use of machine learning in various parts of the render pipeline. We will hence cover a small subset of it relevant to this PhD, specifically targeting the use of compiler techniques in computer graphics. 

\subsubsection{Domain Specific Languages (DSLs) for Computer Graphics} Taichi \cite{huTaichiLanguageHighperformance2019} is a high-performance DSL written for Python that is designed for high performance sparse programs, a class of programs that includes raytraced rendering. LuisaRender \cite{zhengLuisaRenderHighPerformanceRendering2022} and RenderKernel \cite{yangRenderKernelHighlevelProgramming2024} are two attempts at creating a high-level DSL for raster pipelines, attempting to use Python's decorator functionality to specify which pieces of code are kernels to be dispatched to the GPU.

\subsubsection{Inverse Rendering}

Inverse rendering derives geometry and materials from one or more final images of a target scene. This is achieved through machine learning; specifically, the approach of \emph{differentiable rendering} uses \emph{automatic differentiation} (or autodiff) of the shaders to produce geometry and textures that would produce the same target images. State of the art in the field includes Mitsuba (and its underlying IR, DR.JIT \cite{jakobDRJITJustintimeCompiler2022}), which is able to automatically differentiate the whole pipeline and train for both geometry and render simultaneously, and SlangD \cite{bangaruSLANGDFastModular2023}, which performs automatic differentiation at the per-shader level which improves performance but forces geometry and render to be trained separately. Crucially, both papers include performance comparisons with the autodiff in machine learning frameworks such as JAX \cite{frostigCompilingMachineLearning2018} and Enzyme \cite{mosesScalableAutomaticDifferentiation2022}. We include this as an interesting exploration of compiler techniques in computer graphics, and a potential research pivot should initial plans go awry.

\section{Thesis Proposal}

When certain conditions are right, compilers are fantastic at doing certain types of automatic optimization: in particular, loop fusion and loop tiling. However, other types of optimization require guidance, either because transformations are mathematically illegal or because they may interfere with downstream optimizations (known as the undecidable phase-ordering problem \cite{touatiDecidabilityPhaseOrdering2006}). User-schedulable languages provide a means to specify the optimization schedule manually, however, users are required to either specify every step of compiler optimization or leave it up to a previously-derived pipeline. In the domain of GPU programming, where tensor and parallel programs dominate the problem space, we propose that the compiler only needs a little bit of guidance, and all subsequent tilings, fusions, and peephole optimizations may be left up to the compiler to greedily perform.

We are proposing the following chapters, each targeting a different phase of GPU optimization:
\begin{itemize}
  \item Extensible Compiler Optimization of Attention Kernels (In Progress)
  \item Compiling to Accelerate Block-Sparse Linear Algebra with Raytracing Hardware
  \item Automatic End-to-End Optimization of Real-Time Graphics Engines
\end{itemize}

\subsection{Extensible Compiler Optimization of Attention Kernels}

\label{sec:attention}

Collaborator: Kunwar Grover, AMD \\
Workshop Demo: C4ML @ CGO (1 February 2026) \\
Target venue: OOPSLA 2026 (17 March 2026)

The attention mechanism (\autoref{eqn:attention}) is the mechanism that gives large language models the ability to infer context. As it has rather famously been decreed to be "all you need" \cite{vaswaniAttentionAllYou2023}, optimization of attention has become a heavily researched topic \cite{daoFlashAttentionFastMemoryEfficient2022,daoFlashAttention2FasterAttention2023,dongFlexAttentionProgramming2024}, especially with regards to targeting the GPU. The state-of-the-art in the field is PyTorch's FlexAttention \cite{dongFlexAttentionProgramming2024}, which admits a large variety of attention variants by providing two key configuration points: $\mathsf{score\_mod}$ to modify the values of $QK^T$ and $\mathsf{mask\_mod}$, a heavily configurable masking engine. Our key insight is that by manually specifying the optimization of one step of the attention kernel, the rest of the mechanism becomes completely configurable by the user, while leaving the compiler free to perform automatic compiler optimizations that distribute the kernel to the GPU.
\begin{align}
  \label{eqn:attention}
  \quad \Attention(\mathbf{Q}, \mathbf{K}, \mathbf{V}) 
  &= \softmax(\mathbf{Q} \mathbf{K}^T) \mathbf{V}
  \\
  \label{eqn:attention-math}
  &=\left[
    \cfrac {e^{\mathbf{S}_{i,j}}} 
           {\sum_{n=0}^{N} e^{\mathbf{S}_{i,n}}}
    \right]
    \mathbf{V}
    \qquad \text{ where } \mathbf{S} = \mathbf{Q} \mathbf{K}^T
  \\
  \label{eqn:attention-math-safe}
  &=\left[
      \cfrac {e^{\mathbf{S}_{i,j} - m_i}} 
             {\sum_{n=0}^{N} e^{\mathbf{S}_{i,n} - m_i}}
    \right]
    \mathbf{V}
    \qquad \text{ where } m_i = \max_{i}(\mathbf{S}_i)
\end{align}

Our contributions are, and will be, as follows:

\begin{enumerate}
  \item An implementation of an exponential reduction operator, \milakov, that allows tensor compilers to automatically optimize the attention kernel with loop tiling and fusion
  \item An end-to-end implementation of an attention skeleton that flexibly accommodates low-level, element-wise changes to the attention kernel
\end{enumerate}

\subsubsection{Limitations of Optimizing Attention}

Attention (\autoref{eqn:attention-math}) utilizes the $\softmax$ operation to create a probability distribution of the tokens in embedding space. However, taking the exponent of the values in the $QK^T$ results in values that far exceed the range of even 32-bit floating point numbers. To execute on real machinery, a safer version of softmax (\autoref{eqn:attention-math-safe}) is used that normalizes the elements by subtracting the row's maximum, such that the range of the exponentiation rests between 0 and 1. As maximum and accumulation are both reductions, and the denominator's accumulation is dependent on the maximum computation, the loop fusion is impossible for the compiler to perform automatically.

\begin{figure}
  \includegraphics[width=\textwidth]{attention-alg.pdf}
\caption{\label{fig:attention} Optimization of attention. Left is the naive implementation of attention, and on the right, we present how our high-level attention representation can be tiled-and-fused to obtain the FlashAttention-2~\cite{daoFlashAttention2FasterAttention2023} kernel. Values that don't persist between loop iterations are annotated as $\tilde{x}$, borrowing Dao's convention~\cite{daoFlashAttentionFastMemoryEfficient2022, daoFlashAttention2FasterAttention2023}.}
\end{figure}

We define $\oplus_n$ (\autoref{eqn:milakovreduction}), a binary reduction operator on vectors of $n+1$ dimensions that uses its first element to reduce all other elements exponentially, with the syntax borrowed from Milakov's online softmax normalization \cite{milakovOnlineNormalizerCalculation2018}. We then manually fuse the softmax and second matmul of attention into a single nested reduction loop over \milakov, making it tileable.

\begin{equation}
  \label{eqn:milakovreduction}
  \begin{bmatrix} x_0 \\ x_1 \\ \vdots \\ x_n  \end{bmatrix} 
  \oplus_n 
  \begin{bmatrix} x_1  \\ y_1 \\ \vdots \\ y_n \end{bmatrix} 
  = 
  \begin{bmatrix}
    \max(x_0, y_0) \\
    \alpha_x  x_1 + \alpha_y y_1 \\ 
    \vdots \\
    \alpha_x x_n +  \alpha_y y_n \\
  \end{bmatrix}
  ~\mathsf{where}~
  \begin{aligned}
    m &= \max(x_0, y_0) \\ 
  \alpha_x &= e^{x_0 - m} \\
  \alpha_y &= e^{y_0 - m}
  \end{aligned}
\end{equation}

Loop tiling is the transformation that allows us to partition the loop and extract a subtile to become a kernel for the GPU. However, if we are unable to fuse the loop, each loop must be tiled separately, resulting in multiple dispatch calls that could materialize unnecessary temporary tensors and incur scheduling overhead. By rewriting attention using \milakov as in \autoref{fig:attention}, we can decompose it to the corresponding linalg kernels and derive a single nested loop. When tiling this loop by block sizes $B_c$ and $B_r$, we are able to automatically derive the exact same kernel as Flash Attention 2 \cite{daoFlashAttention2FasterAttention2023}.

Unlike Flash Attention, which is implemented in PyTorch as a low-level Triton kernel \cite{pytorchcontributorsTorchnnfunctionalscaled_dot_product_attentionPyTorch272025}, our attention implementation is written as a transformation of a high-level neural network. This allows us to perform subsequent tiling and optimizations on the attention mechanism such as quantization, conversion to MXFP \cite{rouhaniMicroscalingDataFormats2023} formats and other low-level optimizations, while still allowing users to program using the high-level representation.

\subsection{Compiling to Accelerate Block-Sparse Linear Algebra with Raytracing Hardware}

Target Venue: ASPLOS 2026 Summer Cycle (August 2026) \\
Backup Deadline: PLDI 2027 (est. November 2026)

General purpose GPU computing has its origins as a repurposing of the raster pipeline \cite{bolzSparseMatrixSolvers2003,krugerLinearAlgebraOperators2003}, resulting in the pipeline's subsequent generalization and abstraction that culminated in the current year's compute pipeline of launch grids and thread blocks. However, when adapting the general pipeline for raytracing, the limitations of compute were laid clear: as a SIMD architecture, performance would degrade quickly due to the heavy branching and recursion present in raytraced workflows. Thus, the raytracing pipeline (\autoref{fig:raytracepipe}) was introduced, with the ability to reorganize threads \cite{adinetCUDADynamicParallelism2014}, to loop back to previous stages and built-in acceleration of the bounding volume hierarchy traversal. In an attempt to coax lightning into striking twice, work began immediately on utilizing the pipeline for non-geometric workflows. While many of these attempts were successful~\cite{menesesAcceleratingRangeMinimum2024,bauerVisibilityAlgorithmsDynamic2023,haGeneralizingRayTracing2024,Evangelou2021RadiusSearch,hennebergRTIndeXExploitingHardwareAccelerated2023}, reformulating the algorithm as a geometric problem and partionining the program for raytracing requires low-level, domain-specific knowledge of manipulating graphics pipelines and resources. There currently exists no abstraction that maps to the utilization of the raytracing pipeline as perfectly nested loops do for the tiling of the compute pipeline.

This paper will investigate lowering to the raytrace pipeline to as a compiler-driven optimization.

\subsubsection{Abstraction candidates} The natural candidate for abstraction is \emph{sparse linear algebra}. The art of treating linear algebra programs like geometric problems is not new; polyhedral compilers treat the iteration domain and tensors as integer polyhedra \cite{grosserPolyhedralASTGeneration2015}. Conversely, the row and column indices of sparse linear algebra could be typecast as geometric coordinates, and retrieving all sparse elements in a row could be done with a raycast along the row's index. Zhang et al. \cite{zhangRTSpMSpMHarnessingRay2025} devised an algorithm to accelerate sparse matrix-sparse matrix multiplication with raytracing. By specifying the lowering of certain sparse operators to be optimized for RT cores, there is reason to hypothesize that more complex programs could be fused into the subsequent kernels to yield performant GPU kernels. Additionally, block-sparse data structures exist as quads in geometric space, which reduces the number of elements in the BVH, while also taking advantage of the GPU's tensor acceleration.

\paragraph{Hash} A common pattern across the various raytrace-targeted formulations of non-geometric problems is the \emph{hash}ing of the stored elements into a tuple of nine $\mathsf{float32}$ elements. This arises due to the ray-traced pipeline's acceleration structures that are fixed to storing three-dimensional geometry, however, hashing itself is inherent to some of these programs as well.

Taichi \cite{huTaichiLanguageHighperformance2019} is a high-performance user-schedulable language that separates computation from data structures. Computations are always written as if accessing a dense structure, while a separate schedule designates the layout of the data being accessed. Data structures are devised with three structural nodes: \emph{dense} arrays, \emph{dynamic} arrays and crucially, \emph{hash}, lending credence to hash's candidacy as a stand-in for raytrace-accelerated access.

Lastly, if the hash were specified to be \emph{order-preserving}, the accompanying bounding volume hierarchy would be able to take advantage of this feature to cull early in the recursion process.

% \subsubsection{The Future of Ray-traced Accelerators} As current raytracing cores are heavily optimized towards solving the graphics problem, Barnes et. al propose a more generic accelerator, the Hierarchical Search Unit \cite{barnesExtendingGPURayTracing2024}, to abstract the programming model for general purpose. Issues with the current raytracing cores presented are the inability to handle more than three dimensions and the lack of visibility over the BVH data structures.

\subsubsection{Criteria for Success} Achieving an abstraction that lowers to ray-traced acceleration as efficiently as tensor computations do for tiled computation would be a massive success. We have collected a suite of sparse problems that form the state-of-the-art of raytrace-accelerated programs~\cite{menesesAcceleratingRangeMinimum2024,bauerVisibilityAlgorithmsDynamic2023,haGeneralizingRayTracing2024,Evangelou2021RadiusSearch,zhangMLIRLinalgDialect2022,hennebergRTIndeXExploitingHardwareAccelerated2023}, and achieving comparative performance to any of these approaches would prove our abstraction useful and beneficial to adopt in compiler frameworks.

However, we take a realistic lens based on our prior work on attention tiling, and observe that we targeted a very specific program that was very well understood and already had multiple optimized forms proving the viability of the approach. To take aim at all raytrace-acceleratable programs with a single abstraction might prove too lofty an ambition. In this regard, we believe that optimizing a block-sparse linear algebra kernel for raytraced-acceleration with tensor fusion remains viable.

\subsection{Automatic End-to-End Optimization of Real-Time Graphics Pipelines}

Target Venue: SIGGRAPH Asia 2027 (June 2027) \\
Backup: SIGGRAPH 2028 (January 2028)

% 1. We are doing optimization of real-time pipelines as program rewrites 
% 2. Tiled deferred is a surprisingly involved operation, as geometry needs to be tiled as well
% 3. We want to optimize for temporal locality when optimizing for real-time performance.

While advances in rendering techniques have pushed the envelope of real-time rendering techniques closer towards realism over the past decade, the state of programming real-time simulation engines has largely remained the same: program the host in C++ and the device in the shader language of the platform. The historical argument has been that C++ allows fine-grained control over the low-level semantics for performance, however, given the prominence of Python in the machine learning ecosystem to accelerate machine learning models, we would like to question this hypothesis. We will define a user-schedulable DSL for render pipelines, and allow engineers to use a scheduling language (\autoref{fig:deferred}) to guide the transformation while still allowing the compiler to greedily fuse and optimize the resulting render pass. This brings all the benefits of user-schedulable languages --- mainly, the separation of concerns between computation and optimization --- to the world of real-time rendering, allowing for more maintainable code and faster iteration by users.

In this case, we transform the deferred shading pipeline (left) to a tiled deferred shading pipeline (right) that consumes less memory. \subsubsection{State-of-the-art} 
The state-of-the-art for high performance computing DSLs in computer graphics is Taichi \cite{huTaichiLanguageHighperformance2019}, a Python-embedded DSL that has its users specify the data format separately from the computation. Taichi is very performant for its target use case, but it struggles to achieve even cinematic performance of 24 frames per second. We argue that the optimization of the pipeline, performed for many years in real-time simulation engines, and caching of frame-to-frame state is critical to achieving real-time performance.

The state-of-the-art real-time simulation engine for comparison is Unreal Engine 5's Lumen engine \cite{epicgamesLumenGlobalIllumination2025}, which adopts many advanced graphics techniques to achieve realistic graphics. Global illumination is achieved by accumulating light data over several frames, known as \emph{temporal sampling}~\cite{lambruTemporalSamplingRealTime2021}. As with our machine learning compatriats, beating the hand-tuned equivalent is nigh-on impossible, but achieving comparable real-time performance alone would be a fantastic result.

\subsubsection{Reactive programming} A key feature of real-time simulation engines that stands out from offline rendering engines is the expectation of temporal locality, resulting in stateful functions executed from frame to frame. This could be the state of a BVH, or a cached global illumination calculation. The semantics of frame-to-frame state can be captured with an aspect of reactive programming known as \emph{synchronous reactions} \cite{pompougnacWeavingSynchronousReactions2022}.


\subsubsection{Criteria for Success} As control set ups, we have to resort to tutorials by LearnOpenGL~\cite{vriesJoeyDeVriesLearnOpenGL2025} and Sascha Willems~\cite{willemsSaschaWillemsVulkanExamples2025}, as many graphics engines do not make it easy to isolate features of their graphics pipeline for apples-to-apples comparisons. Success is defined by achieving real-time framerates while applying transformations that further optimize the OpenGL/Vulkan tutorial examples with minimal (<20) lines of code expressed as program transformations.

A groundbreaking success would have occurred if either of the following were achieved: 
\begin{itemize}
  \item We surpass Taichi's performance, achieving cinematic performance in their domain without loss in fidelity or significant increase in code complexity.
  \item We can achieve real-time performance in an apples-to-apples comparison with Unreal Engine 5's Lumen Engine \cite{epicgamesLumenGlobalIllumination2025}.
\end{itemize}
